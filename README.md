# LunchInfo 🍲

A lunch-menu aggregator for the area around **Avenyn and Götaplatsen, Gothenburg**
— anchored on Lennart Torstenssonsgatan and reaching Lorensberg, Vasastan,
Heden, Johanneberg, Chalmers and Korsvägen.

Restaurants by district (46 in total): Heden 16 · Vasastaden 12 · Chalmers
campus & Ullevi 6 · Johanneberg 4 · Krokslätt 4 · Lorensberg 3 · Haga 1.

A Python scraper fetches each restaurant's weekly lunch menu from its own
website, validates the data, and writes `site/data.json`. The site itself is
fully static — open it anywhere, no backend needed.

## Live site

**https://rashir4.github.io/LunchInfo/** — hosted free on GitHub Pages, with
HTTPS, and refreshed automatically each weekday morning by
`.github/workflows/deploy.yml`. No domain purchase involved.

## Quick start

```bash
make setup     # create .venv and install dependencies
make scrape    # fetch this week's menus -> site/data.json
make test      # run the test suite
make serve     # serve the site at http://localhost:8017
```

Run `make scrape` each Monday (or put it in cron) to pick up the new week.

## Layout

```
scraper/
  models.py          # Restaurant / Dish dataclasses + validation + dish tagging
  fetch.py           # polite HTTP client (pooling, UA, retries, timeouts, size cap)
  utils.py           # Swedish weekday & week-number parsing (Stockholm time)
  main.py            # orchestrator: scrape all -> dedupe -> validate -> data.json
  restaurants/       # one module per restaurant (auto-discovered)
    _plateimpact.py  #   shared GraphQL client (Chalmers campus restaurants)
    _kvartersmenyn.py#   shared extraction for kvartersmenyn.se-hosted menus
site/
  index.html/app.js/style.css   # static frontend
  data.json          # generated by the scraper
tests/
  fixtures/          # saved HTML snapshots (make fixtures)
  test_*.py          # model, util, parser and output-schema tests
```

## Adding a restaurant

Create `scraper/restaurants/<id>.py` with:

```python
from ..models import Dish, Restaurant
from ..utils import day_key

RESTAURANT = Restaurant(
    id="my-place",              # must match the module name (underscores -> dashes)
    name="My Place",
    address="Gatan 1",
    url="https://myplace.se",
    menu_url="https://myplace.se/lunch",
    walk_minutes=10,
    cuisine="Husmanskost",     # drives the kitchen filter; see models.CUISINES
    price="139 kr",
    lunch_hours="11.30–14.00",
    static_menu=False,         # True if the weekday rotation never changes
)

def parse(html: str) -> dict:
    ...  # return {"mon": [Dish("..."), ...], ..., "fri": [...]}
```

Then save a fixture and test it:

```bash
.venv/bin/python -m scraper.main --only my-place --save-fixtures --dry-run
# note: test ids use the dashed restaurant id, not the module name
.venv/bin/python -m pytest tests/test_parsers.py -k my-place
```

Menus that live in PDFs or JSON APIs can define a module-level `fetch()`
returning whatever text `parse()` consumes. Helpers worth reaching for first:

| Need | Use |
| --- | --- |
| A PDF menu | `fetch.fetch_pdf_text(url)` |
| A JSON/GraphQL endpoint | `fetch.post_json(url, payload)` |
| A Chalmers campus menu | `_plateimpact.fetch_week(unit_id)` + `iter_occurrences(raw)` |
| A kvartersmenyn.se page | `_kvartersmenyn.menu_lines(html, expect_name=...)` |
| A bare weekday heading | `utils.exact_day_key(text)` |
| A date to a day key | `utils.day_key_for_date(date)` |

Parsers do **not** need to dedupe dishes — `main.py` does that at the model
boundary. Never hard-code a week number; use `utils.current_week()`.

Every `Dish` is auto-classified into food types (`veg`, `fisk`, `kott`,
`kyckling`, `gryta`, `pasta`, `soppa`, `sallad`, `sushi`, `nudlar`, `burgare`)
for the site's filter, so parsers need do nothing. Pass `tag="veg"` when the
kitchen labels a dish vegetarian but the text does not say so, or
`tag=NO_TAG` to suppress a badge the text would get wrong.

## Filtering on the site

Four controls, which combine:

| Control | Filters by |
| --- | --- |
| Search box | restaurant name or dish text (accent-insensitive) |
| Restaurant | one specific restaurant |
| Kök | cuisine (Husmanskost, Italienskt, Indiskt, …) |
| Typ av mat | food type — the card then lists only matching dishes |

Add a cuisine to `models.CUISINES` only if no existing label fits; a near-
duplicate ("Svenskt" alongside "Husmanskost") fragments the dropdown, and
`tests/test_regressions.py::TestCuisineCoverage` fails on unknown labels.

## Failure behavior

- A restaurant whose scrape fails is still shown on the site with a
  "couldn't fetch" note and a link to its menu page.
- `main.py` refuses to write `data.json` unless at least half the restaurants
  (and never fewer than 3) scrape cleanly, mirroring the output contract the
  test suite enforces, so a broken run can't wipe a working site.
- A `--only` run refuses to merge into a `data.json` from a different week,
  so last week's menus can never be relabelled as this week's.
- Transient failures (5xx, connection errors) are retried with backoff; 4xx
  responses fail immediately.
- `tests/test_output_schema.py` validates the generated `data.json`
  (shape, day keys, no leaked HTML, majority of scrapes succeeded).

Menus are scraped for personal use; data always links back to the source
restaurant, and walking times are estimates from Lennart Torstenssonsgatan.


## Deploying

The site is static, so hosting is free on GitHub Pages. One workflow
(`.github/workflows/deploy.yml`) both refreshes the menus and publishes.

### First-time setup

1. Create an empty GitHub repo — public, with no README, licence or
   `.gitignore` (Actions minutes are free for public repos, and scheduled
   workflows keep running there).
2. Push this repo to it:
   ```bash
   git remote add origin github-personal:Rashir4/LunchInfo.git
   git push -u origin main
   ```

   `github-personal` is an SSH alias in `~/.ssh/config`, not a typo. GitHub
   refuses to accept one SSH key on two accounts, and the default key here is
   already registered to the work account `alphaleap-rasheed`. The alias pairs
   a dedicated key (`~/.ssh/id_ed25519_avenylunch`) with the personal account,
   leaving plain `github.com` working as before for work repos. Add
   `~/.ssh/id_ed25519_avenylunch.pub` to the personal account under
   **Settings → SSH and GPG keys** first, then check it with:
   ```bash
   ssh -T github-personal     # should greet your personal username
   ```

   Commits are currently authored as `rasheed.sheik@alphaleap.se`. GitHub links
   commits to a profile by email, so to have them show up as yours on the
   personal account, set a repo-local identity before pushing:
   ```bash
   git config user.email "<id>+<username>@users.noreply.github.com"   # from GitHub → Settings → Emails
   git config user.name  "<your name>"
   ```
3. In the repo: **Settings → Pages → Build and deployment → Source:
   GitHub Actions**. (Not "Deploy from a branch" — the workflow uploads the
   site as an artifact.)
4. In **Settings → Actions → General → Workflow permissions**, pick
   *Read and write permissions* so the scheduled run can commit the refreshed
   `site/data.json`.
5. The first deploy runs on push. Check the **Actions** tab; the deploy job
   prints the live URL.

### A shorter URL (all optional, all free)

The Pages URL above costs nothing and needs no upkeep, so this is only worth
doing if the address itself bothers you.

- **Drop the `/LunchInfo` path.** Rename the repo to `Rashir4.github.io` and
  the site answers at `https://rashir4.github.io`. GitHub gives each account
  one such "user site", so this spends it on this project.
- **A free subdomain.** Services like [is-a.dev](https://is-a.dev) hand out
  e.g. `lunchinfo.is-a.dev` via a pull request to their repo. Free, but
  someone else reviews it and you depend on them keeping the service running.
- **Buy `lunchinfo.nu`** (or any free name) (~100–200 SEK/year through Loopia or Websupport;
  `.nu` and `.se` are both run by Internetstiftelsen). Only then add the
  DNS records below — `A` for `@` to `185.199.108.153`, `.109.153`, `.110.153`
  and `.111.153`, plus a `CNAME` for `www` to `rashir4.github.io.` — wait for
  them to resolve, and only after that:
  ```bash
  echo avenylunch.nu > site/CNAME && git add site/CNAME && git commit -m "Custom domain" && git push
  ```
  Adding `site/CNAME` before DNS resolves redirects the working Pages URL to a
  dead domain and takes the site offline, so leave that file absent until the
  domain is genuinely live.

### The scheduled refresh

Runs 05:00 UTC on weekdays — 07:00 Stockholm in summer, 06:00 in winter. It
scrapes, runs the tests, commits `site/data.json` when it changed, and deploys.

Weekdays rather than Mondays only, because some restaurants publish the new
week late; a daily run picks them up the day they appear. For a weekly run,
change the cron in the workflow to `0 5 * * 1`.

A failed scrape does **not** take the site down: the previously committed
`data.json` is deployed instead and the run is marked failed so you get a
notification. `scraper/main.py` also refuses to write a `data.json` where fewer
than half the restaurants scraped cleanly.

Note that GitHub disables scheduled workflows in public repos after 60 days
with no repository activity. The weekly menu commits count as activity, so this
only matters if every scrape stops producing changes.
